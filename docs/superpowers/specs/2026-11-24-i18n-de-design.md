# Deutsche Lokalisierung (station-manager) — Design

**Stand:** 2026-11-24 · **Branch:** `feat/i18n-de` · ein PR

## Problem

Die i18n-Infrastruktur steht (`LANGUAGES` en/de, `LocaleMiddleware`, `i18n_patterns`, EN/DE-Umschalter
in der Topbar, ~1190 `{% trans %}`-Tags, ~36 Python-Module mit `gettext`), aber es gibt **keine
Übersetzungen**: `locale/` fehlt, nichts kompiliert `.mo`-Dateien, und wer „DE“ wählt, sieht Englisch.
Zusätzlich ist `User.language` (Profilfeld) vom Umschalter entkoppelt und wird nur als OIDC-`locale`-Claim
verwendet, und die JS-Strings sind gar nicht übersetzbar.

## Ziele

1. Vollständiges Deutsch für die Web-UI: `locale/de/LC_MESSAGES/django.po` + `djangojs.po`, keine fuzzy-
   und keine leeren Einträge.
2. Build: `.mo` werden **nicht** committet; das Docker-Image kompiliert sie (`compilemessages`), CI auch.
3. CI-Gate gegen Drift: neue markierte, aber unübersetzte (oder fuzzy) Strings lassen CI rot werden,
   kaputte Platzhalter (`msgfmt --check-format`) ebenfalls.
4. Sprache folgt dem User: Login aktiviert `User.language`, der Umschalter speichert für eingeloggte User
   in `User.language`, das Profilfeld wirkt sofort. Anonyme User: weiter Cookie/Browser.
5. JS-Strings über Djangos `JavaScriptCatalog` übersetzbar.
6. **Keine Regression durch deutsche Zahlen-/Datumsformate** (Komma statt Punkt in Attributen, JS,
   Formular-Inputs).

## Nicht-Ziele

- Alarm-Texte (E-Mail/Telegram/Push) werden im Hintergrund ohne Request erzeugt und sind heute nicht mit
  `gettext` markiert → bleiben wie sie sind (eigenes Thema: pro Empfänger `translation.override`).
- Service-Worker (`sw.js`): enthält außer dem Fallback-Titel „OE5XRX“ keine eigenen Texte, Titel/Body
  kommen vom Server → nichts zu tun.
- Admin (`/admin/`) nutzt Djangos eigene Übersetzungen; App-eigene Admin-Labels laufen über die normalen
  Model-`verbose_name`s mit.
- Inhalte, die bewusst nur deutsch sind (z.B. Datenschutz-Hinweistext), werden nicht ins Englische übersetzt.
- Station-Agent (`station_agent/`) hat keine UI → nicht im Katalog.

## Entscheidungen

### Quellsprache = Englisch
Rund 90 `gettext`/`{% trans %}`-msgids sind heute deutsch (z.B. `_("Nur E-Mail")`, `"Vereins-Mitglied"`,
Token-Seiten, Datenschutz-Kurzinfo). Ein englischer User sieht dort Deutsch. Diese msgids werden auf
englische Quelltexte umgestellt, die deutsche Fassung wandert in die `.po`. Damit gilt eine einfache
Invariante: **msgid = Englisch, `de` übersetzt alles, `en` braucht keinen Katalog.** Tests, die auf die
deutschen Texte prüfen, werden angepasst (bzw. aktivieren `de`). Choices-Werte (DB) ändern sich nicht,
nur Labels → keine Datenmigration (Django erzeugt ggf. eine reine `choices`-AlterField-Migration; die wird
mitcommittet).

### Stil der Übersetzung
Österreichischer Amateurfunkverein, **Du-Form** (wie die bestehenden deutschen Texte: „Verwalte deine
Identität“). Natürliches Deutsch, kurz in Buttons/Spaltenköpfen. Glossar (verbindlich, damit die
aufgeteilte Übersetzung konsistent bleibt):

| EN | DE |
|----|----|
| Station, Region, Slot, Modul/Module | Station, Region, Slot, Modul |
| Rollout, Deployment, OTA, Heartbeat, Token, Image, Release, Firmware, Dashboard, Repeater, Squelch, Locator, Preset, Scan(ner), iGate, Topology | Rollout, Deployment, OTA, Heartbeat, Token, Image, Release, Firmware, Dashboard, Repeater, Squelch, Locator, Preset, Scan(ner), iGate, Topologie |
| Alert / alert rule | Alarm / Alarmregel |
| acknowledge / resolve | quittieren / auflösen |
| Callsign | Rufzeichen |
| Sign in / Log out | Anmelden / Abmelden |
| User / Member / Applicant | Benutzer / Mitglied / Bewerber |
| Settings / Save / Cancel / Delete / Edit | Einstellungen / Speichern / Abbrechen / Löschen / Bearbeiten |
| Audit log | Audit-Log |
| Terminal session | Terminal-Sitzung |
| Lock (control lock) | Sperre (Bedien-Sperre) |
| transmit / receive (TX/RX) | senden / empfangen (TX/RX bleibt) |
| Frequency, Tone, Bandwidth | Frequenz, Ton, Bandbreite |
| Archive / Restore | Archivieren / Wiederherstellen |

Platzhalter (`%(name)s`, `%s`, `{}`), HTML-Tags und Entities bleiben exakt erhalten; Pluralformen
(`nplurals=2`) vollständig.

### Katalog-Erzeugung
`makemessages -l de --no-obsolete` mit festen Ignores (`.venv`, `vendor`, `staticfiles`, `tests`,
`station_agent`, `docs`, `scripts`, `node_modules`) — gekapselt in `scripts/i18n.sh` (Subcommands
`make`, `compile`, `check`), damit lokal, CI und Doku denselben Aufruf nutzen. JS-Domain:
`makemessages -d djangojs` über `static/js` und `static/webpush`.

### Build / Docker
`gettext` wird im Dockerfile nur für den `compilemessages`-Schritt installiert und im selben `RUN`
wieder entfernt (`apt-get purge --auto-remove`), Image bleibt schlank. `*.mo` in `.gitignore`.

### CI
- Lint-Job (oder eigener Job „Translations“): `apt-get install gettext`, `scripts/i18n.sh check`:
  1. `makemessages` (beide Domains) in den Checkout,
  2. `msgattrib --untranslated --no-obsolete` und `msgattrib --only-fuzzy` müssen leer sein,
  3. `compilemessages` (nutzt `msgfmt --check-format`) muss durchlaufen.
  Fehlermeldung nennt die betroffenen msgids und den Fix-Befehl (`scripts/i18n.sh make`, übersetzen).
- Test-Job: `gettext` installieren + `compilemessages` vor `pytest`. Zusätzlich kompiliert eine
  Session-Fixture in `tests/conftest.py` die Kataloge, wenn `.mo` fehlt oder älter als `.po` ist
  (lokales `pytest` funktioniert ohne Extra-Schritt).

### Sprache ↔ User
- **Login** (`LoginView.form_valid`): Cookie `django_language` = `user.language`, und die Redirect-URL
  wird per `translate_url` auf das Präfix der User-Sprache umgeschrieben (unpräfixierte Ziele wie
  `/sso/authorize/...` bleiben unverändert; der Cookie sorgt dort für die Sprache).
- **Umschalter**: eigener View `accounts:set_language` (ersetzt im Topbar-Formular `set_language`),
  delegiert an `django.views.i18n.set_language` und speichert bei eingeloggtem User zusätzlich
  `User.language` (`update_fields=["language"]`). Anonyme: unverändertes Django-Verhalten.
  Der bisherige `/i18n/setlang/`-Pfad bleibt erreichbar.
- **Profil**: ändert der User `language` im Identity-Formular, wird Cookie gesetzt und auf die
  Profil-URL im neuen Präfix redirectet.
- **Bestehende Sessions** (7-Tage-Rolling, kein erneuter Login nach dem Deploy): Middleware
  `UserLanguageMiddleware` (nach `AuthenticationMiddleware`) — eingeloggter User **ohne** Sprach-Cookie:
  Cookie auf `user.language` setzen; bei einem GET auf eine präfixierte UI-Seite mit abweichendem
  Präfix (kein HTMX, kein API) einmalig auf die übersetzte URL redirecten. Mit Cookie greift sie nicht
  mehr — eine explizite Präfix-URL (z.B. geteilter `/en/...`-Link) wird respektiert.
- Admin-Edit eines anderen Users ändert nur dessen Feld (wirkt bei dessen nächstem Login).
- Cookie-Flags: `LANGUAGE_COOKIE_SECURE`/`SAMESITE`/`HTTPONLY` analog Session-Cookie in `prod.py`
  (`LANGUAGE_COOKIE_HTTPONLY=False` ist unnötig — JS liest ihn nicht → `True`).

### JS
- `path("jsi18n/", JavaScriptCatalog.as_view(), name="javascript-catalog")` **innerhalb**
  `i18n_patterns` (Sprache aus dem Präfix), `login_not_required` (Login-Seite nutzt ggf. JS-Strings),
  mit `cache_page` (Katalog ändert sich nur pro Deploy). In `base.html` als erstes App-Script mit
  CSP-Nonce eingebunden.
- In allen `static/js/*.js` + `static/webpush/push.js` werden User-sichtbare Strings mit `gettext()` /
  `ngettext()` / `interpolate()` markiert. Die `*-logic.js`-Module laufen auch unter Node
  (`tests/js/*.mjs`) → Fallback-Shim pro Datei:
  `const gettext = globalThis.gettext || ((s) => s);` (analog `ngettext`, `interpolate`).
  Keine String-Verkettung von übersetzten Fragmenten — ganze Sätze mit Platzhaltern.
- Protokoll-/Zustands-Strings, die an den Server gehen oder mit Server-Werten verglichen werden, werden
  **nicht** übersetzt.

### Zahlen & Daten unter `de`
Mit aktivem `de` lokalisiert Django jede Zahl/jedes Datum im Template (`1.5` → `1,5`). Gefährlich ist das
überall, wo Maschinen lesen: HTML-Attribute (`value`, `data-*`, `min/max/step`, `style`), Inline-Scripts,
JSON-artige Strings, SVG-Koordinaten, `<input type=number|date|datetime-local>`. Regel:

- Solche Stellen bekommen `|unlocalize` bzw. `{% localize off %}` oder ein explizites, locale-freies
  Format (`|date:"c"`, `|date:"Y-m-d\TH:i"`, `|stringformat`). `|floatformat` in Attributen nur mit
  `u`-Suffix.
- Date/DateTime-Widgets bekommen ein explizites `format=` (ISO), sonst rendert Django das deutsche
  `DATETIME_INPUT_FORMATS[0]` in einen `datetime-local`-Input.
- Number-Inputs: `lang="en"` bleibt/kommt (siehe Projekt-Regel).
- Absicherung: Tests rendern die betroffenen Seiten unter `/de/` und prüfen, dass die kritischen
  Attribute einen Punkt-Dezimal-Wert enthalten; zusätzlich ein generischer Test, der für eine Reihe
  zentraler Seiten unter `/de/` alle `data-*`/`value`/`min`/`max`/`step`-Attribute auf das Muster
  `^\d+,\d+$` scannt und fehlschlägt.

### Templates ohne Trans-Tags
`navbar.html`, `tower_mark.html`, `_channel_badge.html`, `_alert_badge.html`,
`control/widgets/*.html`: werden durchgesehen; User-sichtbare Texte (Labels, `title`, `aria-label`,
Platzhalter) bekommen `{% translate %}`. Technische Werte (Einheiten, Rufzeichen, Codes) bleiben.

## Tests (Kern)

- `/de/` Dashboard + Login + Profil zeigen deutsche Strings, `/en/` englische.
- Login mit `user.language="de"` → Cookie `de` + Redirect auf `/de/...`; `next=/sso/authorize/...`
  bleibt unpräfixiert, Cookie gesetzt.
- Umschalter: eingeloggt → `User.language` persistiert; anonym → nur Cookie.
- Profil-Sprachwechsel → Redirect auf neues Präfix.
- Middleware: Session ohne Cookie → Cookie + einmaliger Redirect; mit Cookie → keiner; HTMX/API nie.
- JS-Katalog unter `/de/jsi18n/` liefert deutsche Strings, CSP-konform eingebunden.
- Katalog-Hygiene-Test: `.po` hat keine fuzzy/leeren Einträge (polib-frei, via `msgattrib` im CI-Script
  + Python-Test mit `gettext`-Modul gegen die kompilierte `.mo`: Stichproben).
- Locale-Format-Regressionen (siehe oben).
